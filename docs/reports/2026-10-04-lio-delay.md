# LIO delay, EKF yaw and matching cost, 2026-10-04

The incident confirms that delayed LIO exceeded the former EKF history window
and distorted fused yaw. Separate raw-motion experiments also confirm an
incorrect LIO rotation Jacobian that increases matching iterations. They do
**not** reproduce or fully explain the incident's roughly one-second backlog.

This report records findings and their limits. Bags, profiling programs,
temporary instrumented sources, plots, CSV/JSON outputs and local test files are
not shipped. The production change authorized during this investigation was
the EKF history increase from 0.5 to 2.0 seconds. Production LIO was not rebuilt
or instrumented during the investigation.

## Incident and estimator replay

Source recording: `field-held-tf-20261004/trial-bag`, 116.822 seconds and
234,006 messages. It contains raw IMU, rear-axle LIO/wheel/IMU, EKF and
controller outputs, but no raw LiDAR scans or per-frame LIO timing.

LIO receive age, measured as bag receipt time minus source stamp, grew from
about 100 ms to 978 ms before the fault, and peaked near 1166 ms afterward.
The first arrival older than 0.5 s was about 549 ms old. Source scan-end epochs
continued at roughly 100 ms intervals. Receive age includes input wait,
processing, callback scheduling, transport and recording delay; it is not a
measurement of internal computation alone. Delay continued growing during a
period when actual IMU yaw rate decreased, so yaw rate alone does not explain it.

An isolated replay used installed `robot_localization` 3.5.4 and the same
LIO, wheel and IMU messages over bag offsets 65–77 seconds, preserving source
stamps and original receipt order/timing in simulated time. Two filters differed
only in their history length. Both used lag smoothing and prediction to the
current output time; each produced 2400 states from 3106 input messages.

Yaw was aligned at RUNNING onset and compared with short-term raw gyro
integration after subtracting stationary bias:

| Output | Yaw-increment error RMS in the final 1.5 s | Error at fault |
| --- | ---: | ---: |
| Original recorded EKF | 10.87 degrees | -22.97 degrees |
| Replay, 0.5 s history | 10.85 degrees | -22.98 degrees |
| Replay, 2.0 s history | 0.27 degrees | -0.19 degrees |

The 0.5 s replay differed from the original yaw increment by only 0.20 degrees
RMS. This supports history exhaustion as the cause of this estimator anomaly.
The reference is gyro integration, not independent absolute heading truth;
the approximately 23-degree cumulative error is distinct from the approximately
6.6-degree plan-handover mismatch.

Both `params/ekf_rear.yaml` and `params/ekf.yaml` now use
`smooth_lagged_data: true`, `history_length: 2.0` and
`predict_to_current_time: true`. Two seconds is retained history, not an imposed
output delay. Older-measurement replay may increase memory and CPU work. This
mitigates the observed estimator failure but does not make LIO arrive earlier.

## LIO implementation and build identity

For `p_world = R_wi * (R_il * p_lidar + t_il) + t_wi`, the rotation part of the
point-to-plane measurement Jacobian must use the local IMU-frame point:

```text
B = -normal^T * R_wi * hat(R_il * p_lidar + t_il)
```

The incident binary instead used `t_wi`, incorrectly treating world position
as the rotation lever arm. This makes convergence depend on map origin. The
fork source now uses `t_il`, consistent with the
[official FAST-LIO implementation](https://github.com/hku-mars/FAST_LIO/blob/main/src/laserMapping.cpp#L674).
A central finite-difference example agreed with the corrected derivative to
about 9.7e-11; the historical derivative differed by up to 1.80.

At the investigation snapshot, restoring just `t_il` to `t_wi` in the working
source reproduced the complete historical source checksum. The installed
executable still resolved to the October 3 build and matched the earlier
benchmark executable checksum:

| Evidence | SHA256 |
| --- | --- |
| Historical `lidar_processor.cpp` | `4251416066ff5c5020f64b506d3448f9a5fc19534c44f530b06b2c56cee670db` |
| Historical `lio_node` executable | `f9d2825acaba8850caf2475ae78e71ddabad095fc2652f515788006985f071f8` |

Thus the source correction had not entered the installed incident executable.
Publishing the corrected source does not update that executable: deployment
requires a rebuild. The historical byte-based point-selection flags were
already present; a `vector<bool>` race is not established as an incident cause.

## Controlled raw-motion measurements

Two earlier recordings contained raw Livox scans and IMU: the October 3
`venue-20261003-161459/bag` (477 scans, maximum absolute z gyro 0.88 rad/s) and
`mpcc-test-20261003-013910` (714 scans, maximum 3.94 rad/s). These are different
recordings from the incident.

An independent offline core executable compared the historical and corrected
formula with identical inputs, two OpenMP threads and the effective ten-iteration
cap. Input filtering, IMU scaling and filter configuration were held constant.
The first 50 scans were excluded for initialization. Core timing covers
`MapBuilder::process()`; it excludes input delivery, ROS queues, publishing and
the original full-stack workload. The high-turn comparison was repeated in
reverse execution order, giving 1328 measured scans per formula.

| High-turn core measurement | Historical `t_wi` | Correct `t_il` |
| --- | ---: | ---: |
| Mean iterations | 5.57 | 3.37 |
| Mean core duration | 30.80 ms | 19.44 ms |
| Core duration P95 | 55.99 ms | 29.76 ms |
| Mean point-matching duration per iteration | 5.01 ms | 5.08 ms |
| Point-matching share of core duration | 90.52% | 88.02% |
| Scans reaching ten iterations per 664-scan run | 67 | 13 |

Mean core duration decreased by 36.87%. Downsampled point counts were nearly
identical, around 2021 per scan. The saving comes mainly from fewer complete
matching iterations, rather than faster individual matches. Matching includes
point transforms, map-neighbor searches, plane fitting and usable-point selection.
It dominates this experiment; matrix work and map insertion do not.

Consistently shifting both the initial filter position and map, while keeping
the physical input unchanged, further isolates the coordinate dependence:

| World-origin shift, lower-turn recording | Historical mean duration / iterations | Correct mean duration / iterations |
| --- | ---: | ---: |
| None | 17.54 ms / 2.73 | 16.46 ms / 2.56 |
| x=1.75 m, y=4.60 m | 25.01 ms / 4.05 | 16.26 ms / 2.53 |
| x=10 m | 32.93 ms / 5.43 | 16.79 ms / 2.66 |

The middle offset approximates the incident's starting rear-axle world position;
it does not recreate the incident map or pose history.

## Iteration limit and remaining work

`ieskf_max_iter: 5` is read in `lio_node.cpp` but never passed to
`IESKF::setMaxIter`; `IESKF` therefore retains its default cap of ten.
The production wiring remains unchanged. Stopping requires both a rotation
correction below 0.01 degrees and a translation correction below 0.15 mm.
At the cap, the implementation still publishes and updates the map.

Explicitly applying a five-iteration cap in the independent high-turn experiment
gave these results:

| Formula | Mean duration, cap 10 | Mean duration, cap 5 | Cap-5 scans exiting before the stopping condition |
| --- | ---: | ---: | ---: |
| Historical | 30.65 ms | 24.42 ms | 289/664, 43.5% |
| Correct | 19.45 ms | 18.64 ms | 25/664, 3.8% |

Pose differences between cap-five and cap-ten runs are comparisons between
algorithm outputs, not ground-truth accuracy validation. Reducing the cap does
not correct the measurement derivative and has not been approved for production.

The incident bag can reproduce the delayed-input effect on EKF, but cannot
rerun LIO without raw scans. The full cumulative-delay cause remains open:
input lateness, persistent map state, tree rebuilds, output overhead and CPU
scheduling may also contribute. The next vehicle recording should retain raw
scans and IMU from startup, binary/configuration identity, per-frame callback
and stage durations, iterations, queue depth, rebuild events and system load.
No complete version of that instrumentation is currently shipped.

Detailed local evidence remains under `log/lio-causal-investigation-20261004/`
and `log/lio-internal-profile-20261004/`; these ignored directories are absent
from a fresh checkout.

## Publication verification

The staged source snapshot built `fastlio2`, `ackermann_mux`, `aims_mpcc` and
`aims_racer_system` in separate build/install directories. Eighteen local Python
checks, twenty local C++ checks and five isolated ROS integration cases passed.
The ROS cases used the separately built executables. No vehicle driver was
started, and the installed incident LIO executable remained unchanged. Test
sources, fixtures, build outputs and investigation artifacts were excluded
from the publication; these checks do not establish moving-vehicle performance.
