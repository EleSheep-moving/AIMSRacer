# 1.5 m/s 外场试验：速度边界与其余 gate

## 已确认的停车原因

失败轮目录：`/home/aims/aimsracer-data/sessions/2026-10-10/mpcc-acados/185831_v15_n15_independent_lap01`。巡航与硬上限都为 1.5 m/s。bag 中行驶阶段 EKF 速度峰值为 1.54094 m/s；控制器 request 的原生状态码均为 0，但 28 次独立候选校验拒绝，另有 36 次接管拒绝，全部接管拒绝的具名约束为 `speed_bounds`，其余具名输入、转角和转向速率超限均为 0。

例如 seq65 的状态记录有实测速度 1.52831 m/s、decision_speed 1.52602 m/s，候选超限 0.018412。最终 seq179 时速度 1.513958 m/s，旧计划原始 source 年龄 1.270029 s，超过 1.2 s TTL，进入 RECOVERING / Plan expired。完整交付未超时。原因是巡航紧贴硬上限后，实车速度的小幅超调使新候选无法持续接管，而非计算来不及。

按操作员授权，只将新 bundle 的 `max_speed` 从 1.5 改为 4.0 m/s，巡航仍为 1.5 m/s，N15、dt=0.1 s、RTI 和其他配置不变。bundle：`/home/aims/aimsracer-data/experiments/mpcc-acados-runtime/field-20261010/bundle-v15-n15-independent-accel-cap4`。

4 m/s 同时作用于真实速度候选边界、虚拟进度速度上限和输出硬上限；正常一圈的目标/终点速度规划仍受 1.5 m/s 巡航与曲率降速控制。里程计位置跳变检查中 `max_speed * dt + 0.15 m` 的派生容许值也随配置改变。没有把巡航速度设置成 4 m/s。

## 当前相关门限

| 环节 | 门限/条件 | 当前作用 |
|---|---|---|
| 速度 | 0–4 m/s | OCP、独立候选、接管后的执行证书及输出 |
| 纵向输入 | 1.5 m/s 轮为加速/制动各 0.5 m/s²；后续 1.8 m/s 轮各 1.0 m/s² | 独立硬限制 |
| 转向 | 转角 ≤0.45 rad、转向速率 ≤2 rad/s | 独立硬限制 |
| 候选可行性 | 原生 status=0、全部有限、最大超限 <1e-4 | 任意剩余约束失败即拒绝 |
| 执行证书 | 独立滚动检查速度、加减速、转角和转向速率 | 对实际输出采样继续检查，部分边界数值容差约 1e-8 |
| 输入新鲜度 | 里程计源时间/接收时间、导航权限、已应用输入历史均 ≤100 ms | 同时要求历史覆盖状态 epoch |
| 定位 | 地图 SHA 一致、ready、有效 alignment、同一 epoch/anchor | anchor 源与年龄 ≤1 s；health heartbeat ≤0.3 s |
| 接管状态差 | 位置 ≤0.3 m、航向 ≤30°、速度 ≤0.3 m/s、转角 ≤20° | 比较历史输出预测与实际状态 |
| 接管命令差 | 速度 ≤0.3 m/s、转角 ≤20° | 比较真实旧输出与新候选前缀 |
| 求解交付 | 提交至完整交付 ≤50 ms | 超预算计划拒绝 |
| 原始计划寿命 | TTL=1.2 s，预测覆盖 1.5 s | 超寿命进入 RECOVERING，停车或等待连续可用候选 |
| 输出调度 | 发布间隔 >100 ms 则故障；v2 输出 sampler 支持单步 ≤50 ms | 防止丢弃过长输出间隔 |
| 权限 | RC 选择器授权 true；车辆启动速度绝对值 ≤0.1 m/s | 锁车撤销权限；只显式 enable 启动 |
| 里程计跳变 | 位置增量 ≤max_speed×dt+0.15 m；另有姿态/反向速度合法性检查 | 与接管误差检查不同 |
| 其他生命周期 | 地图/epoch 改变、ROS 时钟回退、重复 `/drive` 发布者、终点越过 0.2 m | 触发失效或停车 |

当前关闭：组合加速度椭圆硬约束、corridor 越界停车。`lateral_accel_limit=1.0` 继续用于曲率速度规划；它不再是候选横向加速度硬拒绝条件。`rate_bounded_v2` 的 jerk 与转向加速度参数不构成恢复后的硬约束。CH10 只影响手动油门，不限制导航速度。

## 后续 2.2 m/s 与时钟读取顺序修复

只将巡航目标从 1.8 提高至 2.2 m/s，保留 N15 / dt=0.1 s、max_speed=4、加减速各 1.0 m/s²及其余配置；新 bundle 为 `bundle-v22-n15-accel1-cap4`。独立滞后模型闭环 405 周期通过，求解 P95 0.832 ms、最大 2.914 ms。

首轮数据目录 `191317_v22_n15_accel1_cap4_lap01`：约 6.7 s 时进入 FAULT / ROS clock moved backwards，未完成一圈。操作员确认停车前正常、未接管、已停稳锁车；原始包和日志已归档。

检查发现 `RuntimeNode::odometry` 在拿 mutex 前读取 steady / ROS 时钟，在拿锁后调用 `observe_clock_locked`，其间其他回调可以记录更晚 ROS 时间，使等待中的旧读数被当作大于 1 ms 的回退。已把这两个时钟读取放到持锁后，使全部 ROS 时钟比较按同一锁串行。没有关闭时钟回退门限、改变源消息排序/新鲜度检查或修改系统 NTP。系统校时日志未见对应条目，随后 10 s 采样未见超过 1 ms 的真实回退；这些观察不单独证明首轮一定没有系统回退。

`test_runtime_clock` 的回归检查通过：保留原有输出回调等待测试；增加里程计回调排队、其他回调先记录较新时间的测试，确认不错误失效；模拟真实 2 ms 回退，确认仍进入 FAULT，撤销权限并清空快照。测试运行在隔离 domain 194，驾驶输出 remap，无实车执行器。产物为实验根下 `clock-ordering-build.log`、`clock-ordering-test.log`、`clock-ordering-host-sample.json`。旧二进制备份为 `mpcc_rt_node.before-clock-ordering`。

部署后使用同一物理配置与原生 bundle 重试，目录 `192020_v22_n15_accel1_cap4_lap02_clockfix`：一圈 COMPLETE，477 请求、0 求解失败、0 超时、0 deadline miss，458 激活、19 次接管拒绝，没有再次出现时钟故障。操作员确认行驶正常、未接管，已实际停稳锁车。控制器、录包与负载记录已结束，包、运行日志、源码补丁、回归输出和哈希清单已归档。基础链路、定位和 RViz 继续运行。
