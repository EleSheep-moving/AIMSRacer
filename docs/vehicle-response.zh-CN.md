# 车辆响应与控制器假设

**简体中文** · [English](vehicle-response.md) · [文档索引](README.zh-CN.md)

本指南把当前 V35 控制器模型与已录制的车辆响应联系起来，区分**模型配置参数**、**历史实测结果**和**尚未完成辨识的行为**。

<a id="what-the-current-controller-models"></a>
## 当前控制器建模了什么

| 项目 | 当前实现 | 含义 |
| --- | --- | --- |
| 纵向接口 | MPCC 速度命令 → RC 选择器 → VESC 速度 PID | 优化器中的加速度积分成速度目标，不是直接发送电机加速度命令。 |
| 纵向预测 | `dv/dt = a` | 在配置边界内采用理想加速度，没有单独的速度 PID 延迟或响应状态。 |
| 转向预测 | `dδ/dt = (δcmd − δ) / τ`，`steering_tau: 0.08` | 命令到车身偏航响应的一阶近似，没有单独的纯延迟状态。 |
| 偏航预测 | `dψ/dt = v tan(δ) / [L (1 + K v²)]` | 后轴自行车模型，`wheelbase: 0.36`、`understeer_coefficient: 0.0`。`K` 为零是模型假设，不是实测轮胎无侧滑。 |
| 命令发布周期 / 接管提前量 | 20 ms / 20 ms | 执行调度时间；两个数值都不是执行器延迟的辨识结果。 |
| 加速 / 制动边界 | 1.0 / 1.0 m/s² | 预测与命令的配置限制，不是实测最大牵引或制动能力。 |

`δ` 是**估计的等效转向状态**，不是前轮角度传感器的实测值。`/sensors/servo_position_command` 报告舵机位置命令；收到它不能证明车轮已经到达该角度。实际转发给车辆的命令是 `/ackermann_cmd`，`/drive` 是 RC 选择之前的控制器提议。

当前模型与配置见 [vehicle.yaml](../src/controller/config/vehicle.yaml)、[导出的区间模型](../src/controller/aims_mpcc/backend_models.py)和[原生状态传播](../src/aims_mpcc_rt/src/core.cpp)。状态、控制量与积分方法见 [MPCC 实现](../src/controller/docs/implementation.zh-CN.md)。

### 纵向响应与运行条件有关

速度命令的响应与 **VESC 速度 PID 增益和控制器设置**、**电池/直流母线电压**、电流与功率限制、当前车速、车辆负载及滚动阻力有关。加速和制动的响应也可能不同。因此，拟合得到的延迟与时间常数描述的是录制时的工况，不是适用于所有条件的车辆常数。

[vesc.yaml](../src/aims_racer_system/params/vesc.yaml) 中的 ERPM 与速度换算决定命令/测量的尺度，不能代替电机控制器 PID 整定或可用扭矩的辨识。对照不同运行时，应记录 VESC 固件配置、PID 增益、相关限制、电池电压与电量状态、负载和速度范围。现有数据尚未建立随电压变化的定量响应模型。

<a id="pure-delay-response-constant-and-estimation-lag"></a>
## 纯延迟、响应时间常数与估计滞后

对阶跃命令，带纯延迟的一阶响应可用以下模型辨识：

```text
t < D:   y(t) = y0
t ≥ D:   y(t) = y0 + (u − y0) [1 − exp(−(t − D)/τ)]
```

- **纯延迟 `D`：** 响应开始之前的等待时间。
- **响应时间常数 `τ`：** 等待结束之后的变化速度。一阶阶跃经过一个 `τ` 达到最终变化量的约 63.2%，经过 `2.3τ` 达到约 90%。
- **估计滞后：** 控制器看到的状态所具有的测量年龄、滤波与历史处理影响。它与电机、舵机和底盘响应分别考虑。

当前转向参数 **0.08 s** 是没有显式 `D` 的单一集中拟合。它不代表“80 ms 后车轮才开始动”“80 ms 达到 90%”，也不是单独测得的舵机时间常数。不重新拟合 `τ` 就再加一个实测起响应延迟，可能重复计算同一部分滞后。

50 Hz 命令定时器以比最高 20 Hz 求解请求更高的频率采样计划，不会让执行器瞬间响应。同样，200 Hz EKF 发布不会让延迟的 LIO 测量变成当前测量；源时间戳与延迟测量处理仍然重要。

<a id="what-the-recorded-measurements-support"></a>
## MPCC 计算与命令交付

保存的参考轨迹在离线阶段准备。在线 MPCC 反复优化接下来 **15 × 0.1 s = 1.5 s** 的运动，不会在每次请求中优化整圈。预测时域表示未来时间范围，不是计算耗时。bundle 生成/编译及节点启动也与运行中的控制周期分开统计。

运行链路为：**最新 EKF/地图条件 → 请求快照与运动预测 → acados 求解与候选检查 → 结果交付 → 定时接管与执行检查 → `/drive` → RC 选择器 → `/ackermann_cmd`**。

2026-10-10 的两轮 V35 NX 外场同时运行 FAST-LIO2、EKF 和 NDT。按请求编号重新串联原始日志得到：

| 计时区间，P95 | V35 第一次 | V35 第二次 |
| --- | ---: | ---: |
| 原生求解器调用 | 2.32 ms | 1.36 ms |
| 请求快照 → 候选结果交付 | 4.00 ms | 2.66 ms |
| 请求快照 → 首次使用已接管新计划发布 `/drive` | 39.51 ms | 39.75 ms |
| 请求快照 → 首个匹配的 `/ackermann_cmd` | 44.28 ms | 44.33 ms |
| EKF 源时间戳 → 首个匹配的 `/ackermann_cmd` | 50.29 ms | 46.62 ms |

请求到候选结果统计覆盖 **635 / 457 次请求**；新计划首次 `/drive` 统计覆盖 **531 / 442 次成功接管**；`/ackermann_cmd` 链路覆盖 **428 / 427 个能够无歧义匹配的非零首条命令**，排除了零值、重复或歧义线缆命令。后者从 EKF 源时间戳到命令的中位数为 **40.56 / 40.40 ms**，观测最大值为 **55.67 / 60.81 ms**。这些是观测样本，不是最坏情况保证；635 / 457 次请求均未超过配置的交付期限。

为什么几毫秒计算会变成几十毫秒交付？请求预测在 `submitted + 20 ms` 接管；达到该时刻后，由下一个 20 ms 输出节拍执行接管检查并发布命令。计算与提前量重叠，因此**求解时间 + 20 ms + 20 ms 不是固定的正确相加方式**。随后 RC 选择器按配置的 200 Hz 转发。发生变化的非零线缆命令中，`/drive` 到 `/ackermann_cmd` 的实测延迟中位数为 **5.13 / 4.98 ms**，P95 为 **6.31 / 6.03 ms**，覆盖 **1,094 / 1,100 对匹配命令**。不能把各阶段独立的分位数相加，当作端到端分位数。

**50 ms `solver_timeout`** 限制的是请求到候选结果交付，不是 EKF 源时间戳到命令、任意新传感器样本到达后到命令，或车辆物理响应的总时限。求解请求最高 20 Hz：新条件到达后可能等待下一次请求，已有计划继续按 50 Hz 输出。请求始终获取最新合格快照；上面没有对每条到达输入都跟踪一次新的求解。

复算使用 NX 会话 `192955_v35_n15_accel1_cap4_lap01` 与 `193524_v35_n15_accel1_cap4_lap02` 的原始 `controller/runtime.csv`。按 `sequence` 关联 `request`、成功的 `activation` 和首次 `publish`，用发布的 `steady_s` 减去 `submitted` 或 `source_epoch`。再按唯一的 float32 线缆速度/转向组合及消息时间戳匹配录包中的 `/drive` 与 `/ackermann_cmd`。速度模式下选择器清零加速度元数据，因此不使用该字段匹配。本地分析保存在 `/home/elesheep/aimsracer-data/sessions/2026-10-11/mpcc-command-latency/`；原始数据位置见[外场复盘](reports/2026-10-10-mpcc-field-review.md)。

**这里的终点是命令发布。** 驱动/串口传输、电机、舵机与底盘响应仍需分别测量；发布 `/ackermann_cmd` 不代表车辆已经开始响应。EKF 源状态年龄也不能代表所有上游 LIO 测量的完整年龄。

## 已有实测支持哪些结论

以下结果来自 **2026-09-28 速度模式校准分析**，主要处于约 1 m/s。它们是历史证据，不是新完成的高速辨识：

| 测量 | 报告结果 | 解释 |
| --- | --- | --- |
| 速度命令 → 轮速拟合 | 约 **40 ms 纯延迟 + 0.16 s 响应时间常数** | 包含 VESC 闭环速度控制与传动响应。两个拟合参数相互关联，目前均未作为纵向模型参数。 |
| IMU 持续前向加速度起响应 | **45–60 ms**，中位数 **52 ms**，11 次直线起步 | 经过滤波的起响应检测，不是电机首次运动的精确时刻。 |
| 单一滞后转向拟合 | 使用轮速 **0.0806 s**；使用 LIO 速度 **0.0798 s** | 在已测工况下支持当前 `steering_tau: 0.08` 的集中近似。 |
| 独立转向阶跃的偏航响应 | 起响应中位数 **52 ms**，50% **109 ms**，90% **159 ms**；10 次事件，约 **0.88–1.03 m/s** | 根据 IMU 与速度推算的车身偏航响应，不是机械车轮角度的实测响应。 |

更早的响应分析也发现，约 **48 ms 纯延迟 + 20–27 ms 响应时间常数**的更丰富模型能够解释较陡的转向阶跃。这些数值属于另一种拟合与事件筛选，不能原样叠加到当前 0.08 s 集中参数上。

偏航响应包含舵机、轮胎、底盘与车速的影响。高速下偏航稳定更慢，本身不能证明舵机限制随车速变化。现有记录尚未辨识覆盖不同车速、电池状态与负载的完整加速/制动模型。

原始方法与限定条件见[速度模式校准](reports/2026-09-28-speed-mode-calibration.md)和[车辆响应分析](reports/2026-09-28-vehicle-response.md)。[2026-10-10 外场复盘](reports/2026-10-10-mpcc-field-review.md)提供后续跟踪结果，不能代替执行器辨识。历史报告保留原语言与配置背景。

<a id="how-to-use-this-in-the-next-tuning-session"></a>
## 下一次调参如何利用这些信息

1. 使用**实际转发的 `/ackermann_cmd`**，与带源时间戳的轮速、LIO/EKF 运动和去零偏 IMU 偏航角速度对照。分别记录命令发布时刻、测量时刻与接收时刻。
2. 分开统计静止起步、加速、制动和稳态过弯；按速度区间，在 PID、电压和负载条件可比时比较预测残差。速度尺度错误或陈旧状态也可能表现得像执行器模型错误。
3. 保持坐标系与单位一致。`base_link` 位于后轴中点；原始 Livox 加速度使用 `g`，后轴适配器转换为 m/s²；角速度使用 rad/s。详见[架构](architecture.zh-CN.md)。
4. 根据重复出现的实测失配，决定是否重新拟合集中转向滞后、引入单独纯延迟，或辨识纵向响应模型。即使优化器按理想加速度预测，当前速度模式接口仍有自己的闭环响应。
5. 修改 `steering_tau` 等模型参数后，**重新导出并编译求解器 bundle**，再用它启动。修改源码 YAML 不会改变正在运行的固定 bundle。运行时记录 bundle/配置；流程见[参考与 bundle 指南](../src/controller/docs/usage.zh-CN.md)。
