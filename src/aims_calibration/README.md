# Longitudinal calibration

[简体中文](README.zh-CN.md)

`aims_calibration` measures longitudinal behavior through the existing vehicle command selector. It publishes only native `vesc_msgs/VescCommand` requests on `/calib/vesc_command`, at 50 Hz, stamped with current ROS time and `base_link`. Command and safety/status timers use steady time so they continue checking freshness when `/clock` pauses. The selector owns `/vesc/command`; this package never publishes `/drive` or the driver topic.

The executable and node-only launch are `longitudinal_calibration` and `longitudinal_calibration.launch.py`. The complete graph is `aims_racer_system/calibration.launch.py`. Package launch arguments: `config`, `reference_directory`, `vehicle_config`, `pp_config`, `log_directory`, `stage`, `steering_source`, and `auto_start`. Use the full system graph to configure vehicle, known-map localization, recording, and acceleration estimation. Defaults are disabled; explicit `/calib/enable` (`std_srvs/SetBool`) starts preparation. `auto_start` must be false; the node rejects true, requiring explicit service enable. `/calib/status` reports state, reason, measured current, requested current, and output directory.

## Stages

- `speed_hold`: targets default `[1, 2, 3]` m/s. After one continuous second within 0.2 m/s of the target, collect a continuous ten-second window of actual motor current. Unstable speed, a turn, or straight-region exit invalidates the window; a later straight begins a new trial.
- `accel_interval`: prepare at configured `start_speed` in speed mode, then apply each explicitly supplied positive `currents` entry in `MODE_CURRENT`. The response starts only after that current request appears in the final selected command. End at or above the configured larger `end_speed`. A fresh wheel-speed crossing immediately requests zero speed even if motor telemetry has not advanced or the requested current has not yet appeared in the final command; those incomplete response records are unsuccessful.
- `decel_current`: prepare at configured positive `start_speed` in speed mode, then apply explicitly supplied negative `currents` in `MODE_CURRENT`. End at or below the configured positive `end_speed` (default 0.5 m/s), then immediately request zero speed regardless of motor-telemetry uniqueness or current confirmation. If the boundary wheel observation arrives without new current telemetry, stop and mark the result unsuccessful. Never request reverse intentionally.

Current stage defaults have an empty `currents` array and intentionally refuse startup. Copy `config/calibration.yaml`, set an explicit current list and interval, and select the stage and steering source. The package launch uses explicit `stage` and `steering_source` arguments to override those YAML entries; pass both arguments when choosing a current stage or RC steering. Example accel settings: `stage: accel_interval`, `currents: [5.0, 10.0]`, `start_speed: 1.0`, `end_speed: 2.0`. Example decel settings: `stage: decel_current`, `currents: [-3.0, -5.0]`, `start_speed: 2.0`, `end_speed: 0.5`. These are configuration examples, not validated vehicle current recommendations. If a stable preparation speed already reaches the end boundary (for example, a narrow interval overlapping the stable-speed tolerance), the trial stops at zero speed without issuing any nonzero current and is recorded as not started. Trials time out after 8 s by default; unsuccessful responses have no calculated mean acceleration. Bounds are at most 100 A and at most `min(config.max_speed, vehicle.max_speed, 4)` m/s. There is no automatic sweep or inferred base-current offset. If using measured base current to choose a list, calculate and review the explicit signed values before startup.

The VESC driver's current startup helper must be false in the calibration vehicle graph. Do not run these trials with the driver's 40 A current substitution enabled: the final requested current is not the measured motor current.

## Steering and trial windows

`steering_source: pp` uses `aims_pp`'s recovered enhanced PP implementation, geometry from `vehicle_config`, `NumericReference`, and the same qualified localization and map identity gates as standalone PP. Tuning defaults are lookahead gain 1, minimum 0.3 m, maximum 4.5 m, heading gain 0.1, and curvature feedforward gain 0.1. `pp_config` optionally overrides tuning. Geometry, forward heading, pose continuity, source stamps, health epoch, and map hash must agree. When the vehicle profile enables `enforce_corridor`, the shared PP association also checks the vehicle footprint against reference widths. PP follows the lap at `recovery_speed` outside marked straight windows and uses speed mode while preparing.

PP requires `reference_directory/reference.json` and an explicit `calibration_regions.json` exported by the editor. Region schema is `{schema_version: 1, reference_sha256: "<hash of exact reference.json bytes>", regions: [{id: "straight1", name: "straight 1", kind: "straight", start_s: 2.0, end_s: 10.0}]}`. Progress uses the reference knot/chord coordinate. Intervals include their start and exclude their end. `start_s > end_s` wraps over the closed lap seam; equal endpoints and overlapping regions are rejected. A manual straight mark does not verify available distance, curvature, tire grip, or safe current. Exiting or switching region ends the incomplete trial unsuccessfully; samples from separated windows are never combined.

`steering_source: rc` needs no localization or reference. Wheel odometry supplies velocity. The explicit default profile matches the vehicle launch: `steering_ch1_throttle_ch3_aux_ch5_to_ch10`, steering CH1, throttle CH3, lock CH5, ESC CH6, source CH7, calibration CH8, limit CH10. Values are 1-based. Center is 992, endpoints 172/1810, steering reversed, selector steering scale 0.4751 rad. Sampling is eligible only within the 50-count steering deadzone, with fresh valid RC, unlocked CH5 >= 992, and calibration CH8 > 992. A turn invalidates an incomplete trial and returns to speed mode; the operator may steer while recovering. `sequential_ch1_ch2` is available only when the selector uses that explicit profile (steering CH2, lock CH3, calibration CH7). Confirm the selected profile before any current-stage test.

## Authority, freshness, and stops

While disabled at startup, fresh zero-speed requests let the selector establish calibration selection. Enabling waits for fresh `/control/calibration_enabled == true`, then requires independent RC validity, new wheel/current data, and a fresh final `/vesc/command` corresponding to a recently sent request. The selector restamps commands, so content is matched against a short request history rather than requiring the latest request timestamp. Only the active mode target is populated; positive and negative current both use `MODE_CURRENT`. `MODE_BRAKE_CURRENT` and `MODE_ACCELERATION` are never emitted.

Authority loss, RC lock/mode loss, source/receipt age over 0.2 s, invalid telemetry, foreign final command, map/localization withdrawal, backward ROS/source time, frozen ROS time, timer stall, or another calibration publisher latches `FAULT`, invalidates the current trial, and continuously requests zero motor current until explicit re-enable. Operator disable also invalidates the incomplete trial and requests zero motor current. Re-enable establishes a new ROS-time baseline, clears cached observations and request history, and starts preparation. Authority, RC, wheel, and motor source observations must arrive after the new arm time, and a newly sent zero-speed request must appear in the final command before preparation can move. Runtime clock rollback still latches a fault; explicit re-enable can recover in the new clock domain without waiting for the old timestamp. It never resumes a partial interval. Stage completion requests zero speed. A zero-current request is a coast request, not a physical stop guarantee; the external selector and operator retain control.

## Evidence and metric definitions

Each node run creates a UTC-named directory below `log_directory` with `observations.csv`, `runtime.csv`, atomic `trials.json`, and `trials.csv` once a trial exists. JSON contains effective configuration, vehicle hash, reference and region hashes for PP, and the explicit RC profile. Effective PP values and file SHA-256 (when a tuning file is supplied), calibration YAML SHA-256 (through the package launch), and a canonical effective-configuration hash are retained. A bounded background queue writes evidence; overflow or writer errors invalidate acquisition and request zero current. If the just-completed boundary record cannot be enqueued, its trial success is revoked, `evidence_valid` is false, `mean_acceleration` is unavailable, and `response_completed` retains whether the response had crossed its endpoint. A pending result checkpoint retries once the queue can accept it. `trials.json` is the authoritative acceptance checkpoint: the CSV checkpoint completes first, and a writer error immediately attempts to publish rejected JSON results independently of the failed CSV path, including when no later result is queued. The CSV may retain an earlier checkpoint after a write failure; inspect JSON metadata and diagnostics for evidence validity. Writer failures also invalidate response records whose evidence checkpoint has not completed. JSON metadata retains evidence errors; persistent storage failure remains visible in diagnostics even if the disk cannot retain a new checkpoint. Diagnostics expose pending and dropped queue counts. `runtime.csv` retains ROS time, callback duration (through acquisition enqueue), timer interval, queue counts, and state for later joint-load analysis. It does not prove ARM timing. Raw observations include source wheel and telemetry stamps, wheel velocity, `state.current_motor`, `state.voltage_input`, electrical RPM (`state.speed`), requested and selected targets, authority, steering/window flags, and optional acceleration estimate, source stamp, and quality status. Missing or stale acceleration is recorded as unavailable and never replaces interval wheel-speed response.

Only `/sensors/core.state.current_motor` supplies actual motor current. `current_input`, `avg_iq`, and target current are never substitutes. A row needs both source stamps to advance; timer repetitions never duplicate an observation. Stable and response windows use wheel source time. Current interval samples begin only when both physical source stamps are at or after the first selected-current command stamp (`first_current_ack_stamp`). That bound is latched once; later republished command stamps do not exclude valid delayed telemetry. Current interval response is `(measured end speed - measured start speed) / (end wheel stamp - start wheel stamp)` only for successful trials. Boundaries are the first eligible observed crossing; no interpolation is implied. Telemetry current and wheel velocity have separate stamps, so the CSV retains their offset. Stage A mean and population standard deviation use the eligible actual motor samples in a continuous stable straight window. A current interval already crossed on its first selected-current sample is unsuccessful because its source-time duration cannot be measured. These statistics describe telemetry samples, with no claim of independent noise or bench-calibrated current accuracy.

Tests run in ROS Humble without hardware. Source and synthetic tests demonstrate software behavior; they do not establish physical stop distance, current accuracy, realtime guarantees, or safe field currents.
