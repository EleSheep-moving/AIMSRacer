## Assessment

A useful low-speed prototype, not yet a validated racing controller. The review found two reproducible estimator problems, including a problem introduced by the recent acceleration-fusion change. Prior passing low-speed integration tests did not establish high-speed estimator accuracy. No production configuration or runtime code was changed during this review.

Scope: current AIMSRacer checkout, ROS Humble robot_localization source, new IMU/odometry adapters, MPCC solver/supervisor, RC and VESC conversion. No hardware, Orin timing, real scan matching, tire model or brake testing was performed. The user explicitly declined an additional LIO-loss watchdog; no such change is proposed as an immediate implementation task here.

## 1. P1: lateral accelerometer fusion conflicts with the EKF motion model in fast turns

Location: `src/aims_racer_system/params/ekf_rear.yaml:167` and the acceleration input generated by `scripts/imu_to_rear_axle.py:87`.

The rear-axle correction removes sensor lever-arm terms, but the resulting acceleration is still physical inertial acceleration expressed in body axes. It is not the derivative of body-frame velocity components. In planar motion, `dv_y/dt = a_y - yaw_rate*v_x` and `dv_x/dt = a_x + yaw_rate*v_y`. In a constant-speed circle, body lateral velocity can remain zero while a_y is nonzero.

Humble robot_localization's prediction directly uses acceleration states to increment body velocity components; see [ekf.cpp](https://github.com/cra-ros-pkg/robot_localization/blob/humble-devel/src/ekf.cpp#L270). This mismatch was exposed by the experiment below. Correct gravity and lever-arm compensation alone do not fix it.

Recommendation: for the current general-purpose EKF, treat disabling ay fusion as an interim candidate (diagnostic results support it). Longer term, validate an estimator whose prediction includes rotating-body velocity dynamics, or use FAST-LIO's high-rate propagated state. Do not relabel a velocity derivative as physical sensor acceleration on an ordinary IMU topic. Ax also requires reassessment once lateral velocity/slip is significant.

## 2. P1: delayed LIO corrections are not handled at their measurement epoch

Location: `src/aims_racer_system/params/ekf_rear.yaml` has no `smooth_lagged_data` or `history_length`; defaults leave smoothing disabled. `sensor_timeout: 0.001` is also far below the nominal 5 ms IMU interval and can trigger prediction to wall time between measurements.

A scan-matched LIO state can arrive after the EKF has processed newer IMU measurements. With smoothing disabled, old measurements can correct a newer filter state without rewinding/replaying it. References: [ros_filter.cpp](https://github.com/cra-ros-pkg/robot_localization/blob/humble-devel/src/ros_filter.cpp#L568), [filter_base.cpp](https://github.com/cra-ros-pkg/robot_localization/blob/humble-devel/src/filter_base.cpp#L193).

Recommendation: measure actual source-to-arrival delays, test delayed-data smoothing/history and output-time prediction settings together, and measure replay CPU cost on Orin. A 0.5 s history was only a diagnostic trial, not a validated production setting. This issue concerns measurement-time alignment, not the declined LIO-loss watchdog.

## 3. P1 before faster driving: prediction and command application time are not fully aligned

Locations: `aims_mpcc/node.py:167`, `runtime.py:161`, `worker.py:93`.

Solver starts from the received state without rolling it forward under actually applied controls to anticipated actuation time. The supervisor selects a later point on the new plan based on age, which is helpful, but the skipped portion of that new plan was never applied while the optimizer was running. A 10 Hz replan and 50 Hz command interpolation do not constitute a 50 Hz freshly optimized controller. Solver deadline is 150 ms; horizon is 15*0.1=1.5 s.

Recommendation: measure sensor-to-actuator latency and jitter on Orin, align the optimization initial state with command application time using applied-command history, then choose solve rate/horizon. This is a code-level concern; this review did not quantify its closed-loop tracking penalty.

## 4. P1 before racing: prediction model and actuator dynamics remain assumptions

Locations: `aims_mpcc/solver.py:42`, `aims_mpcc/history.py:11`, `config/vehicle.yaml:19`, `src/vesc/vesc_ackermann/src/ackermann_to_vesc.cpp:141`.

MPCC predicts acceleration as directly achieved (`v_dot=a`) but executes speed targets through the VESC speed loop. There is no identified longitudinal response in the OCP. Steering is estimated from commands with assumed tau=0.115 s and no measurement correction. No lateral-velocity/yaw-rate dynamics or tire saturation states are modelled; a kinematic lateral-acceleration constraint does not model slip.

Recommendation: characterize speed-loop and steering response with modest maneuvers, check ERPM-to-ground-speed conversion and braking distances, then validate horizon prediction errors on held-out data. This does not require current calibration. Use a dynamic/identified model when measured slip/model errors justify it. Raising `max_speed` alone is insufficient.

The current 0.5 m/s cruise, 1 m/s maximum and 1 m/s² lateral limit deliberately prohibit racing. For example, 5 m/s on a 5 m radius requires 5 m/s² lateral acceleration, above that configured envelope.

## 5. P2: manual-driving shadow mode still cannot perform the advertised workflow

Locations: `aims_mpcc/node.py:135`, `node.py:162`, `runtime.py:99`.

Shadow activation still requires autonomous RC selection, and manual takeover deactivates it. Active shadow also estimates steering from hypothetical preview commands rather than actual RC-forwarded commands. This is unsuitable for judging controller predictions while a person drives.

Recommendation: separate preview activation from actuator authority and always estimate the actual vehicle state from applied commands; keep hypothetical rollout steering separate. This is an existing acknowledged limitation, not fixed by the frame migration.

## 6. P1 deployment precondition: recorded odom references have no session alignment

Locations: `aims_mpcc/path.py:159`, `node.py:99`.

Recorded path metadata names `odom`, but does not tie the path to an odometry session, map, or initial-pose alignment. Restarting localization can change the numeric odom origin while retaining the same frame name. Start proximity/heading checks may reject a stale path, but do not constitute a general origin-alignment mechanism.

Recommendation: first runs should record and execute without resetting localization. For reuse, store a map/session association and apply an explicitly validated alignment transform.

## 7. P2: corridor and progress logic are simplified

Locations: `aims_mpcc/path.py:62`, `solver.py:83`, `node.py:118`.

Projection is globally nearest with no previous-progress search window, so neighboring track sections can produce progress jumps under localization error. The reference has constant left/right widths; footprint clearance is tested against a local tangent strip, not a measured boundary polygon or obstacle map. This is acceptable only with a conservative, checked corridor and simple track geometry.

Recommendation: add progress-local association and physically surveyed corridor widths/clearance before complex tracks or racing-line optimization. Current objective strongly tracks reference speed/path; it is not a validated minimum-lap-time planner.
